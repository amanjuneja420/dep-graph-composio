IMPORTANT REWRITE — generalization fix (read this if continuing)
--------------------------------------------------------------------
An earlier version of this session hardcoded a GitHub-specific `ENTITY_ALIASES` dictionary
(issue, pull_request, repository, ...). An advisor review caught that this directly violates
the README's stated requirement ("your generator should generalize... works for any toolkit,
not just this one") — on a non-GitHub catalog, `entitiesFromSlug` would return `[]` for nearly
every tool and the whole qualified-matching pathway would collapse to ~0 edges, failing the
has-edges gate on exactly the property the grader said they'd check.

Fixed by making entity/leaf vocabulary 100% catalog-derived (see DESIGN.md for full
rationale): `buildVocabulary()` walks the WHOLE catalog first to discover entity names (from
$ref titles) and which leaf field names are "distinctive" (appear under ≤2 distinct entities
catalog-wide) vs. generic. Matching then uses fuzzy token/substring comparison
(`entityMatchesWord`) instead of a fixed dictionary. Proven against a committed fake,
zero-GitHub-vocabulary catalog: `fixtures/fake_toolkit_catalog.json` (a made-up "Linear"
ticket-tracker toolkit) — run
  node --import tsx src/generate.ts fixtures/fake_toolkit_catalog.json
and it correctly produces 10 edges (e.g. LINEAR_LIST_PROJECTS -> LINEAR_LIST_TICKETS via
project_id) from a schema shape the code has never seen. This fixture is the actual evidence
for the generalization claim — don't delete it.

HOW THE GENERATOR WORKS (src/generate.ts)
-------------------------------------------
Full rationale in DESIGN.md. Summary:

1. Heuristic schema matching (deterministic, no network, catalog-derived, this is what's
   actually shipped right now since the LLM pass never got verified live — see "OPEN ISSUE"
   below):
   - Pass 1, `buildVocabulary(tools)`: walk every tool's outputParameters catalog-wide
     (resolving $ref/$defs, array items, nested objects via `walkOutputLeaves`) to collect
     (a) the set of all entity names seen (from $ref titles, e.g. `issue`, `pull_request` —
     or, on a different toolkit, whatever nouns it uses) and (b) which leaf field names are
     "distinctive" (appear under <=2 distinct entities catalog-wide, e.g. `tag_name`, `sha`)
     vs. generic (appear under many, e.g. `id`, `name`, `number`) — NO fixed dictionary.
   - Pass 2, `buildHeuristicEdges(tools, vocab)`: for each tool's required input field, try a
     bare match against a distinctive leaf key, or split at the last underscore and fuzzily
     match the prefix against a vocab entity (`entityMatchesWord`: token match or substring —
     `repo` vs `repository`, `pull` vs `pull_request` — derived from the catalog's OWN entity
     names, not a hardcoded alias table).
   - `entitiesFromSlug(slug, vocab)` figures out which catalog entities a tool's own slug
     refers to (for fields sitting directly on a response root, e.g. GITHUB_GET_AN_ISSUE's
     top-level `number`) by fuzzy token match against the pass-1 vocabulary — again, no fixed
     keyword list.
   - CAPS producers per (consumer, field) at 6 — preferring list/get/search/find/query-verb
     tools first (more natural "precursor" actions) — because without a cap, extremely common
     fields like `repository_id` were matching 1000+ producers and drowning the graph in
     low-value edges (first uncapped attempt: 8515 edges; capped: ~2650, much better
     signal-to-noise).
   - `inferService(slug, vocab)` reuses `entitiesFromSlug` for the optional Node.service field.
   - PROVEN to generalize (not just claimed): `fixtures/fake_toolkit_catalog.json` is a
     committed 7-tool fake "Linear" catalog with zero GitHub vocabulary; running the generator
     against it produces 10 correct edges. See IMPORTANT REWRITE above.

2. LLM refinement (`refineWithLLM`, OPTIONAL, gracefully degrades):
   - Only runs if `OPENAI_API_KEY` is set in env (also reads `OPENAI_BASE_URL`,
     `OPENAI_MODEL` — defaults to `openai/gpt-4o`, matches the README's OpenRouter-style
     instructions).
   - Batches heuristic candidate edges (10 per batch, capped at DEPGRAPH_LLM_MAX_EDGES=2000
     total, concurrency 5) grouped with producer/consumer descriptions, and asks the model to
     confirm/reject each candidate as a real dependency vs. a coincidental field-name match.
   - `max_tokens` is capped at 200 per batch (verdict JSON is small; see OPEN ISSUE — this
     was NOT capped in the very first test run and that's what burned the credit budget).
   - ANY failure (missing key, network error, JSON parse failure, 402, whatever) makes that
     batch fall back to "keep all candidates as-is" — never crashes, never drops edges due to
     an LLM hiccup. Logs a per-batch `kept N/M` line and a final summary line
     (`LLM refinement summary: X/Y kept (Z rejected), W/N batches fell back`).
   - This has NOT been verified end-to-end with real reject/keep decisions yet (see below).

OPEN ISSUE — LLM refinement pass is unverified live
------------------------------------------------------
What happened this session:
  1. First test run (BEFORE max_tokens was capped) ran ~130/134 batches against the user's
     real OpenRouter-backed key (base_url https://litmus-production.up.railway.app/proxy/openai/v1,
     model openai/gpt-4o) and only failed near the end with a 402 "requested up to 16384
     tokens" credits error. This almost certainly burned most of the assessment's credit
     budget, since the SDK was defaulting max_tokens to a huge completion ceiling per request
     across ~130 successful large completions.
  2. I capped max_tokens (first to 1024, then to 200 after seeing it still failed) and had the
     user re-run. Second run: ALL 134 batches failed immediately with
     "402 ... can only afford 8 [tokens]" — i.e. the account's credit balance is now
     essentially zero, not a bug in the capped code, just a drained budget.
  3. Every failed batch correctly fell back to keep-as-is (that's the fallback working as
     designed), so the shipped dependency_graph.json / graph.html are 100% heuristic-only
     right now (2528 edges, all from pass 1). LLM refinement code is real and wired in, but
     has never actually returned a real "reject" decision that we've observed — we only know
     it fails closed correctly.
