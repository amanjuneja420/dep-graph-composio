HOW THE GENERATOR WORKS (src/generate.ts)
-------------------------------------------
Two-pass design:

1. Heuristic schema matching (deterministic, no network, this is what's actually shipped
   right now since the LLM pass never got verified live — see "OPEN ISSUE" below):
   - `extractProducibleFields(tool)` walks a tool's outputParameters (resolving $ref/$defs,
     including array-item entities like `Issue`/`PullRequest` and one/two levels of nested
     objects) and registers "qualified" candidate fields, e.g. an `Issue` object's bare
     `number` property becomes the candidate `issue_number` (because it's inside an
     Issue-typed context). Generic leaf names (id/number/name/key/node_id/slug) MUST be
     qualified by an entity to be registered; distinctive leaf names (sha/ref/login/email/
     tag_name/branch) are registered both bare and qualified.
   - For fields sitting directly on a tool's response root (e.g. GITHUB_GET_AN_ISSUE's
     top-level `number`), the entity context comes from scanning the TOOL'S OWN SLUG for
     known entity keywords (`entitiesFromSlug`), since the wrapper schema's own title
     (e.g. "GetAnIssueResponse") isn't a reliable entity name.
   - `ENTITY_ALIASES` maps canonical entities to the short forms Composio/GitHub actually use
     in parameter names (pull_request -> pull/pr, repository -> repo, organization -> org,
     etc.) so e.g. a producer's qualified `pull_request_number` also registers as
     `pull_number`, matching consumers that require exactly `pull_number`.
   - `extractRequiredInputs(tool)` just reads `inputParameters.required`.
   - `buildHeuristicEdges` matches each tool's required fields against the producer index,
     excludes self-loops, and CAPS producers per (consumer, field) at 6 — preferring
     LIST/GET/SEARCH/FIND-verb tools first (more natural "precursor" actions) — because
     without a cap, extremely common fields like `repository_id` were matching 1000+
     producers and drowning the graph in low-value edges (first uncapped attempt: 8515
     edges; capped: 2528, much more sane signal-to-noise).
   - `inferService(slug)` reuses `entitiesFromSlug` for the optional Node.service field.

2. LLM refinement (`refineWithLLM`, OPTIONAL, gracefully degrades):
   - Only runs if `OPENAI_API_KEY` is set in env (also reads `OPENAI_BASE_URL`,
     `OPENAI_MODEL` — defaults to `openai/gpt-4o`, matches the README's OpenRouter-style
     instructions).
   - Batches heuristic candidate edges (10 per batch, capped at DEPGRAPH_LLM_MAX_EDGES=2000
     total, concurrency 5) grouped with producer/consumer descriptions, and asks the model to
     confirm/reject each candidate as a real dependency vs. a coincidental field-name match.
   - `max_tokens` is capped at 200 per batch (verdict JSON is small; see OPEN ISSUE — this
     was NOT capped in the very first test run and that's what burned the credit budget).
   - ANY failure (missing key, network error, JSON parse failure, 402, whatever) makes that
     batch fall back to "keep all candidates as-is" — never crashes, never drops edges due to
     an LLM hiccup. Logs a per-batch `kept N/M` line and a final summary line
     (`LLM refinement summary: X/Y kept (Z rejected), W/N batches fell back`).
   - This has NOT been verified end-to-end with real reject/keep decisions yet (see below).

     real OpenRouter-backed key (base_url https://litmus-production.up.railway.app/proxy/openai/v1,

  2. I capped max_tokens (first to 1024, then to 200 after seeing it still failed) and had the
     user re-run. Second run: ALL 134 batches failed immediately with
     "402 ... can only afford 8 [tokens]" — i.e. the account's credit balance is now
     essentially zero, not a bug in the capped code, just a drained budget.
  3. Every failed batch correctly fell back to keep-as-is (that's the fallback working as
     designed), so the shipped dependency_graph.json / graph.html are 100% heuristic-only
     right now (2528 edges, all from pass 1). LLM refinement code is real and wired in, but
     has never actually returned a real "reject" decision that we've observed — we only know
